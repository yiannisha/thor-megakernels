# Cooperative two-CTA residency on Thor

The opt-in multi-CTA path admits up to two logical workers per physical SM. It uses cooperative launch, checks compiled occupancy before launch, and synchronizes the grid before interpreting queues. All workers must fit in the resident cooperative grid; queue dependencies cannot rely on an unscheduled producer. Physical SM count and logical worker count are separate values. The static scheduler validates queue dependencies before launch.

A resource probe identified an additional occupancy constraint: using named CTA barrier 15 makes ptxas reserve 16 barriers, limiting the candidate to one CTA/SM. The selectable multi-CTA path instead uses full-CTA barrier 7, leaving consumer collectives on 0/3/4. The reduced configuration compiles to 384 threads, 64 registers/thread, eight named barriers, and 85,103 total shared-memory bytes, admitting two CTAs/SM. Forty workers therefore fit on the 20-SM Thor. The default keeps its existing barrier assignment.

The initial pipelined 8-KiB, eight-consumer-warp, one-stage candidate passes numerical replay tests but **fails full-model racecheck**. The same hazards occur with 20 workers, so the evidence does not attribute the race to two-CTA placement. Racecheck identifies attention output conversion writes in shared memory followed by O-projection weight reads after page reuse. Per-thread page arrivals, collective release, producer/acquirer proxy fences, and acquiring all destination pages before publishing the TMA transaction barrier did not independently clear the report. Failed runs remain recorded; numerical PASS does not override a sanitizer failure.

`configs/thor/multi-cta-8k-joined.json` enables a conservative execution-role join at each instruction boundary. All execution warps use named barrier 6 before advancing; the controller is excluded and retains prefetch. This barrier is distinct from consumer and full-CTA barriers. Every execution role traverses the same padded instruction row count. Queue dependency validation and cooperative residency remain required. This serializes inter-instruction execution-role overlap and is an experimental correctness control, not a default optimization.

The joined candidate passes full-model racecheck with zero reported hazards and 90 frozen-cache numerical checks in `multi-cta-joined-page1-*`. Replay p50 is 11.350 ms and p99 14.753 ms under shared GPU load. The standard 16-consumer-warp, three-stage baseline separately passes full-model racecheck (`baseline-pipelined-page1-racecheck.*`). These tests do not establish that every pipelined configuration is safe.

Earlier pipelined 20/40-worker replay medians were 11.358/11.602 ms, respectively; there is no demonstrated multi-CTA speedup. Both failed the same four steps of the 100-step accumulated-cache numerical test (10/21/44/55), despite matching all greedy tokens. Worst logit NRMSE was 3.4744%. These are failed qualification results, not waived errors. Temporal qualification of the joined candidate remains pending.

Expanded synccheck identified divergent participation at the original joined barrier: the TK helper emits `bar.sync`, which is equivalent to `barrier.sync.aligned`, but the execution roles call from separate control-flow branches. The initial racecheck PASS is therefore insufficient to qualify that join. The replacement uses non-aligned `barrier.sync 6, count` with an explicit compiler memory clobber. Its rebuilt binary passes memcheck, synccheck and racecheck with zero errors/hazards (`multi-cta-joined-unaligned/`). All prior evidence stays associated with its original binary. See [PTX barrier semantics](https://docs.nvidia.com/cuda/archive/12.1.1/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-bar-barrier).

The superseded aligned-join qualification is recorded separately in `multi-cta-joined-current/`: source/build provenance, three sanitizer tools, and contexts 128/1024/8192 with seeds 1/2/3. See its process records for actual completion status. Initial malformed sanitizer-filter invocations are retained separately from corrected commands. No configuration is promoted until its exact current binary passes the required checks.

Current H100/B200 and Thor builds succeed in `handoff-final-builds.json`, with the same source hash as the corrected qualification. This matches the earlier reduced pipelined configuration and separates the reported synchronization fix from the unresolved numerical qualification.

This is same-cache context-1024 replay under uncontrolled shared load, not autoregressive latency or a controlled speedup.
