# Architecture and progress invariants

The VM assigns one instruction queue to each persistent CTA. A controller fetches instructions and allocates pages; loader, launcher, storer and consumer warps coordinate through shared semaphores. Llama additionally polls global completion counters across CTAs.

Worker indexing now uses `blockIdx.x`; define `MK_PHYSICAL_WORKER_IDS` to retain upstream `%smid` indexing for controlled comparisons. This change alone does not make arbitrary grids safe: queue count must equal launch CTAs and every potentially waiting CTA must be resident. The checked demo binding now queries native occupancy and actual static/dynamic shared memory before launch; the binding compiles and imports, but its model-tensor runtime path still needs tests. Physical-ID comparisons require queues covering physical SM IDs.

Thor dynamic allocation reserves thirteen pages plus 1023 bytes for worst-case alignment; static bytes are queried from the compiled kernel before launch. The existing layout uses two instruction slots and thirteen 16-KiB pages. Weight prefetch has three stages of four pages each, plus an activation page. Release permutations now derive from lifetime order through a shared C/CUDA arithmetic helper; compatibility and randomized host lifetime tests pass. Per-op parties, native page reuse, static storage and alignment still require joint validation before enabling reduced-stage layouts or multiple resident CTAs.

Host DAG assignment now predicts start as max(worker availability, dependency completion). It rejects missing producers, duplicate node identities and cycles, and resets graph state between assignments. Equal serialized instructions remain distinct operations. Queue validation checks every operation appears exactly once and adds worker queue-order edges to the dependency graph; a cycle in that union is rejected. A seeded 100-DAG host stress test covers varying costs, fan-in, duplicate/missing assignments and predicted dependency timing. This proof covers only the supplied DAG, not opcode counter expectations or GPU visibility.

Global visibility remains unresolved: Llama's volatile counter reads and atomicAdd completion publication lack an explicit acquire/release argument. Do not interpret passing host scheduler tests as CUDA memory-order correctness.

Experimental variants (locality, ready queue, 2 CTA/SM, segmented persistence) are not enabled. Their implementation requires separate occupancy, visibility and activation handoff validation. BF16 is the only upstream precision under consideration; FP8/NVFP4 support is unproven.

Thor can select static allocation or dynamic setmaxnreg redistribution. Explicit architecture-specific codegen is necessary: the earlier generic-PTX validation failure did not prove an SM110a instruction gap. The original H100/B200 dynamic register path compiles with explicit architecture-specific codegen. The pinned TK overlay adds missing compiler memory clobbers around semaphore wait/test-wait asm.

Instruction publication/reuse now uses 32 arrivals per warp on Thor, with every thread signaling. The old 1-arrival-per-warp path remains available as `MK_INSTRUCTION_BARRIER_PARTIES=1` for diagnostics, but the tuner rejects it because racecheck reported shared-memory hazards. A two-warp shared-buffer ping/pong experiment reproduced those reports with aggregated arrivals and passed with per-thread arrivals. Explicit warp synchronization and wait memory clobbers alone did not remove the VM reports; the source and reports do not establish whether every original report was a hardware race or an instrumentation limitation. The new per-thread VM path passed the 8-warp racecheck workload. Full opcode pipeline page/barrier tests remain required.

Matvec consumer/storer ring semaphores also use per-thread parties on Thor: consumer count = consumer warps * 32, storer count = 32. Loader TMA-arrival transaction expectations remain one producer plus expected bytes. This removes a QKV scratch-buffer hazard reported by racecheck while preserving the same pipeline depth and page layout. Per-operation page-finished counters still use the upstream page-lifetime protocol and need targeted reuse tests.

Thor's global completion counters now use device-scope `cuda::atomic_ref`: acquire polling and acq_rel RMW publication. RMWs serialize and carry the publication of prior producers; every producer must finish its TMA/global writes before publishing. Host counter resets precede the kernel on the same stream. Explicit warp joins were added after multi-lane TMA completion before page release/publication. The historical volatile/atomicAdd path remains selectable with `MK_PORTABLE_GMEM_BARRIERS=0` for diagnostics; its memory-order correctness is not established. `MK_GMEM_TIMEOUT_CYCLES` enables a per-thread debug watchdog for global polling, while parent process timeouts cover whole executions.

Attention DAG dependencies now include all four Q heads and their K/V producers. Up/gate instructions split large block lists to stay within the 32-word instruction format, including with 12 logical workers. Native binaries expose a source fingerprint, and correctness tools reject stale binaries after source changes. This prevents a failed rebuild from silently testing an older extension.

The optional ordered-downprojection experiment adds acquire waits and DAG producer edges between reduction columns, preserving a fixed order of BF16 residual updates. It made repeated outputs deterministic on the tested case, but raw logit NRMSE at context 128 was 4.279%, worse than some unordered runs; at context 1024 it was 1.235%. This is a numerical tradeoff/negative result, not a selected optimization.

## Selectable FP32 down-projection finalization

`MK_FP32_DOWNPROJ=1` / `configs/thor/fp32-downproj.json` replaces four BF16 atomic residual updates with four unique FP32 partial writes and a deterministic final sum. Scratch is 4×2048 FP32 values (32 KiB global memory), shared across layers. Each output block has four producers and a counter in reserved barrier slots 7..9 (ordinary opcodes use slots 0..6). The last arriving producer finalizes that block; it does not wait for an unscheduled producer. Every producer fences its lane's writes and joins its warp before lane zero publishes through an acq_rel RMW. The finalizer acquires the RMW chain, joins the warp, sums columns 0..3, rounds the linear result to BF16, adds the BF16 residual, and publishes completion after fenced writes. Each finished block adds four to the original down-projection completion count, preserving its 512-count contract. The next layer cannot reuse scratch until all blocks have published.

Required invariants: exactly one instruction owns each (column, output block); counters are zeroed before launch; reserved counters are not used by other opcodes; no layer begins using scratch before prior-layer completion. `ordered_downproj` is incompatible and rejected because its column-progress counter has a different meaning. This variant removes BF16 atomic arrival-order nondeterminism; it does not by itself prove parity with the whole reference model.

`MK_MATCH_TORCH_BF16_EPILOGUES=1` additionally rounds Q/K projections before RoPE, up/gate projections before SiLU, and the SiLU result before multiplication. `configs/thor/reference-rounding.json` combines that switch with FP32 down-projection finalization. Historical fused-float epilogues remain selectable. Both switches are recorded in native resource metadata and checked by the model and synthetic adapters.

`tools.thor.teacher_forced` compares successive steps with reference past KV and checkpoints each state's logit/hidden/K/V errors. `tools.thor.layer_check` runs isolated layer prefixes from reference layer inputs to separate local operation error from error propagated through earlier layers. Neither diagnostic substitutes for free-running sequence validation.

## Cooperative admission for persistent Thor grids

Thor configurations now use `cudaLaunchCooperativeKernel`; preflight requires the device cooperative-launch capability and checks compiled occupancy and grid capacity. Every thread reaches a `cooperative_groups::this_grid().sync()` at entry, before warp-role branching or dependency waits. Thus no worker starts consuming dependency queues before every worker has reached admission. This replaces the insufficient assumption that theoretical occupancy alone makes an ordinary launch safe under external contention. H100/B200 keep their ordinary launch path. The generated-project template now inherits the matching base config, queries the actual worker count, and uses the checked binding.

The CUDA [cooperative-groups programming guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cooperative-groups.html#when-to-use-cudalaunchcooperativekernel) specifies cooperative launch support and grid synchronization. This is a progress mechanism, not a guarantee of bounded response time under arbitrary external workloads. Process watchdogs remain required. Historical latency datasets used ordinary launches and are not silently relabeled as cooperative measurements.

## Weight pipeline staging and reduced shared memory

Thor's `MK_WEIGHT_PIPELINE_STAGES` selects 1, 2 or 3 input stages. Each stage still contains four 16-KiB pages for a 16×2048 BF16 weight stripe. `MK_PAGE_COUNT` must be at least `1 + 4*stages` and at most 13. The compatibility configuration remains 3 stages/13 pages; minimal reduced layouts use 1/5 and 2/9. Attention keeps its independent three-stage K/V ring within two pages. Output scratch keeps three stages because up/gate retains a pair until its epilogue consumes both.

The existing generic semaphore indices and iteration phases now use the selected input-stage count. Loader reuse waits for all consumers of that slot; consumers wait for TMA completion and output-slot availability; the final use releases each weight page once per consumer warp. Unused pages are released before activation and last-used weight stages through the shared arithmetic header. The same header's host tests exercise minimum and padded layouts and repeated random reallocation. Zero-iteration QKV explicitly drains RoPE TMA because its empty storer never waits for that transfer.

The `tools.thor.stage_matrix` harness builds each selected layout, checks all nine opcode types, all Q/K/V branches, a partial-attention tail, empty-first reduction, and five zero-iteration/reuse cases (matvec → NoOp → matvec → NoOp → matvec). It can run Compute Sanitizer and optional 5-warmup/3×30 full-model replay timing. Every timed repeat retains its original numerical gate. A failed gate suppresses the latency summary. Use a fresh output directory for each invocation so earlier failures remain evidence.

## Compensated BF16 attention probabilities

`MK_COMPENSATED_ATTENTION=1` adds a second BF16 tensor-core product for the residual discarded when FP32 softmax numerators are rounded to BF16. For numerator P, the two operands are `hi=bf16(P)` and `lo=bf16(P-float(hi))`; the accumulator adds both `hi @ V` and `lo @ V`. The denominator remains FP32. This improves intermediate probability accuracy while retaining BF16 Q/K/V and output storage; it costs another P×V MMA and is separately selectable. The default remains the historical single-product algorithm.

Online-softmax initialization now sets the previous scaled maximum to negative infinity, yielding an exact zero first rescale. The earlier zero initializer could evaluate `0 * infinity` for finite, uniformly large negative scores. Q=8/K=-8 reproduces 256 NaN outputs in the old source; the corrected path matches the uniform-softmax reference exactly. This correction applies to both probability variants.

The optimized SDPA backend is not an exact arithmetic oracle. At the tested token-13/position-1025 case with identical frozen past KV, FlashAttention vs PyTorch math differs by 4.9192% raw logit NRMSE; compensated native vs math differs by 1.1114%. Installed torch 2.13's SDPA docstring states that the math backend keeps BF16-input intermediates in FP32. The [official SDPA documentation](https://docs.pytorch.org/docs/2.14/generated/torch.nn.functional.scaled_dot_product_attention.html) describes the same behavior and backend-dependent numerical differences. Both comparisons are retained; changing a reference must be explicit and must not reinterpret historical failures.

`MK_FP64_RMS=1` is an optional diagnostic that accumulates RMS squared sums in FP64, casts variance to FP32, then follows the existing BF16 normalization rounding points. It uses aligned double partials in instruction scratch, with an explicit budget below the reserved RoPE area. This probe gave identical 100-step records to the FP32 control and remains off. It is not evidence for using higher-precision variance in the selected runtime.
